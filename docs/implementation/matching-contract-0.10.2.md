# 0.10.2 · 匹配输出契约与安全字段诊断

日期：2026-09-16；基线0.10.1。全部旧发行目录保留，不迁移或清空正式数据库。

## 已确认与未确认

用户确认网页读取恢复，但所有协议匹配报通用 `AI_RESPONSE_FORMAT`。此错误由业务结果校验阶段抛出，不等同于网络、模型探针或流完成失败。本轮没有用户真实响应、API Key、简历，也未调用真实供应商。

使用虚构资料建立红测试：

```text
npx tsx --test tests/matching.test.ts tests/p10-p11-service.test.ts
旧实现：10 tests / 4 pass / 6 fail
```

六项失败分别为提示词示例自校验失败、冗余派生字段误拒绝，以及四协议服务层丢失具体来源校验错误。

**确认了代码缺陷，但不能将其宣称为用户实际每次失败的唯一原因。** 实际响应究竟在哪个字段失败，需要用户用新版复测后的安全错误码与字段路径确认；不索取原始响应或简历。

## 修复

1. 示例的status从拼接枚举改为合法单值met，recommendation改为consider，枚举在示例外逐项说明。明确布尔值、数组、唯一ID、空证据、来源用途与原文引用要求；示例自身通过parseMatch。
2. 不再要求模型输出coverage/hardGates；即使模型返回这些字段也忽略它们，只从已验证requirements重新计算和保存。不放宽hard、status、引用或recommendation校验。
3. 来源清单统一包含本页非空粘贴文字与附件文字；字段id保持与校验器一致。附件正文仍通过materialContent只发送一次，图像无可验证文字时不允许伪造引用。
4. 校验器返回安全的程序生成字段路径：AI_MATCH_JSON、AI_MATCH_FIELD、AI_MATCH_SOURCE、AI_MATCH_QUOTE、AI_MATCH_EVIDENCE；服务层保留已知校验异常。未知异常仅返回AI_MATCH_INTERNAL，绝不回显任意异常文本。
5. 区分JSON不完整、字段类型/枚举错误、来源错误、引用不匹配、缺少经历证据。所有错误都保持历史与正文不变，不自动增加预算、续写或重试收费请求。
6. 拒绝畸形evidence（不再将任意非数组值静默转为空数组）；无证据须显式[]。保留原有NFKC/空白兼容，不引入模糊匹配、翻译匹配、来源猜测或静默改写状态。

## 用户复测

正常关闭旧版并完整解压0.10.2，不同时运行不同版本。先核对简历PDF抽取文字与岗位正文，在匹配页手动勾选材料、确认协议/模型/预算再发送。支持纯粘贴和附件两种路径。

若仍失败，仅需反馈新版版本号、`AI_MATCH_*`错误码、完整字段路径及说明（例如requirements[0].evidence[0].quote）、协议、是否使用PDF及是否可见抽取文字。不要提交密钥、简历、完整模型响应。SOURCE不等于没有能力，QUOTE也不等于资格不符；它们表示模型证据引用未通过验证。
